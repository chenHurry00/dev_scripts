# 服务器运行状态与用户训练参考方案

> 本文档仅整理方案与接口边界，当前阶段不修改代码。

## 一、目标

在现有中心面板与 `5002` GPU 门户基础上，补充一套**服务器实时运行状态展示**，解决两个问题：

1. 管理员在仪表盘中快速判断：
   - 哪些服务器在线；
   - 哪些服务器当前负载高；
   - 哪些服务器磁盘或内存紧张；
   - 哪些服务器还有 GPU 空闲余量。
2. 普通用户在 GPU 门户中快速判断：
   - 当前是否适合启动训练；
   - 哪些服务器整体更空闲；
   - 是否存在 CPU / 内存 / 存储紧张情况。

## 二、当前现状与问题

当前服务器页主要使用 Agent `/checks` 返回的内容。

这类数据更偏向：

1. Docker 是否正常；
2. GPU 容器能力是否具备；
3. 可写层磁盘限额是否支持；
4. 挂载根目录是否存在。

它本质上是**能力检查**，不是**实时运行状态**。

因此当前界面虽然能知道：

1. 服务器能不能被接入；
2. 支不支持 GPU；
3. 支不支持 rootfs 限额；

但不能直接回答：

1. 这台机器现在 CPU 忙不忙；
2. 内存是否快满；
3. GPU 是否还有空卡；
4. Docker 根目录或挂载盘空间是否紧张；
5. 用户现在适不适合开训练。

## 三、设计原则

### 1. “能力检查”和“运行状态”分开

界面语义必须明确区分：

1. `检查`
   - 表示服务器功能是否满足接入要求；
   - 偏静态、低频变化。
2. `运行状态`
   - 表示服务器当前负载与资源余量；
   - 偏动态、高频变化。

不能继续把实时负载塞进当前“检查”列里，否则含义会混乱。

### 2. 管理端和用户端共用一份中心缓存

不建议：

1. 后台页面自己现查一遍 Agent；
2. GPU 门户再自己现查一遍 Agent。

建议：

1. 中心面板后台统一采样所有服务器；
2. 结果缓存在中心面板内存；
3. 管理端与门户都读取这份缓存。

这样可以避免：

1. Agent 被重复轮询；
2. 管理端与门户状态不一致；
3. 多人同时打开页面时对中心和 Agent 造成额外压力。

### 3. 门户只给“训练参考”，不暴露内部细节

用户门户允许看到服务器整体忙闲程度，但不应泄露过多内部信息。

因此门户中：

1. 可以显示服务器别名；
2. 可以显示 CPU / 内存 / GPU / 存储状态；
3. 不显示宿主机 IP；
4. 不显示挂载真实路径；
5. 不显示其他用户容器名；
6. 不显示 GPU UUID、PID、进程级细节。

## 四、管理端建议展示的信息

建议在仪表盘新增一个 `服务器运行状态` 区块，每台服务器一张卡。

每张卡建议显示以下信息。

### 1. CPU

显示：

1. `CPU 总利用率`
2. `load1 / load5 / load15`
3. `load1 / CPU 核数`

作用：

1. CPU 利用率高说明当前计算压力大；
2. `load1 / cores` 可以补充判断是否存在排队。

### 2. 内存

显示：

1. `已用 / 总量`
2. `使用率`
3. `SWAP 已用 / 总量`
4. `SWAP 使用率`

作用：

1. 判断当前是否还适合开大训练；
2. 避免用户启动后因宿主机内存紧张导致整体变慢或 OOM。

### 3. GPU

显示：

1. `活跃卡数 / 总卡数`
2. `总显存已用 / 总显存`
3. `平均 GPU 利用率`
4. 默认显示前 `2~4` 张最忙 GPU
5. 其余 GPU 折叠为 `+N GPU` 入口，按需展开显示全部 GPU

其中“活跃卡”的判断建议仍沿用当前 GPU 计算时统计口径：

1. 利用率达到活动阈值；或
2. 显存占用达到活动阈值。

默认折叠时建议优先展示：

1. `GPU汇总`
2. 当前最忙的 `2~4` 张卡
3. 剩余卡数折叠入口，例如 `+4 GPU`

展开后每张 GPU 建议继续显示：

1. `GPU 编号`
2. `利用率`
3. `显存已用 / 总量`
4. `当前颜色状态`

### 4. 存储

不建议直接展示整机所有块设备。

第一版只展示平台真正关心的文件系统：

1. `DockerRootDir` 所在文件系统；
2. 已注册 `mount_roots` 所在文件系统；
3. 对相同挂载点去重后展示。

每个文件系统显示：

1. `已用 / 总量`
2. `剩余量`
3. `使用率`

作用：

1. 判断容器可写层空间是否紧张；
2. 判断用户工作区所在盘是否紧张。

### 5. 辅助信息

建议补充：

1. `受管容器数`
2. `最近采样时间`
3. `当前状态标签`

## 五、服务器管理页建议调整

当前服务器管理页建议保留现有列：

1. 服务器名称
2. 主机地址
3. Agent 端口
4. 挂载根目录
5. 检查
6. 容器数
7. 状态
8. 操作

建议改为：

1. 服务器名称
2. 主机地址
3. Agent 端口
4. 挂载根目录
5. 检查
6. 运行状态
7. 容器数
8. 状态
9. 操作

其中：

### 1. 检查列继续保留原语义

显示：

1. GPU 容器支持是否正常；
2. 可写层磁盘限额是否支持；
3. 挂载根目录检查结果；
4. 警告数量。

### 2. 运行状态列新增实时摘要

不建议继续使用左侧堆叠的多行文本摘要。

建议改为每台服务器一张横向卡片，卡片内部使用圆形模块展示核心指标。

建议模块顺序：

1. `CPU`
2. `内存`
3. `SWAP`
4. `Docker`
5. `Workspace`
6. `GPU汇总`

每个圆形模块建议包含：

1. 圆心主值，例如 `71%`、`3/8`
2. 指标标题，例如 `CPU`、`GPU汇总`
3. 一行副文本，例如 `Load 18.2 / 64`、`VRAM 76 / 192 GB`

如果服务器 GPU 较多，则默认只显示最忙的前 `2~4` 张卡，其余通过 `+N GPU` 模块展开。

## 六、仪表盘建议新增的内容

建议在现有四个概览卡片下方新增 `服务器运行状态` 卡片区。

作用：

1. 打开后台第一页就能看到全局忙闲；
2. 不必切到服务器页再逐台查看；
3. 适合作为日常巡检入口。

建议布局：

1. 桌面端按 `2~4` 列服务器卡片网格显示；
2. 每台服务器卡片内部使用圆形模块横向排布并自动换行；
3. 移动端改为 `2~3` 列模块网格；
4. 状态标签固定单行显示，不允许被挤成两行。

## 七、GPU 门户建议展示的信息

GPU 门户不应直接变成“管理员监控页”，但需要提供足够的训练参考。

建议在现有门户首页新增一个 `当前训练环境参考` 区块。

### 1. 全局摘要

建议显示：

1. `在线 GPU 服务器数 / 总数`
2. `空闲 GPU 数 / 总 GPU 数`
3. `资源紧张服务器数`
4. `最近采样时间`

### 2. 每台服务器卡片

每台服务器显示：

1. 服务器名称
2. 当前状态标签
3. CPU 使用率
4. 内存使用率
5. SWAP 使用情况
6. 活跃 GPU 数 / 总 GPU 数
7. 总显存已用 / 总显存
8. Docker 空间状态
9. 工作区空间状态

门户中同样建议使用圆形模块卡片视图，而不是把状态信息塞进狭窄表格列。

默认展示模块建议为：

1. `CPU`
2. `内存`
3. `SWAP`
4. `Docker`
5. `Workspace`
6. `GPU汇总`

门户中的 GPU 展示规则建议为：

1. 默认只显示 `GPU汇总` 和最忙的前 `2~4` 张卡；
2. 剩余卡数显示为 `+N GPU`；
3. 用户点击后仅展开当前服务器卡片中的 GPU 详情；
4. 展开后仍保持圆形模块样式，不切换成表格。

### 3. 对用户真正有帮助的判断

门户需要帮助用户回答的不是“系统细节是什么”，而是：

1. 当前有没有空闲 GPU；
2. 当前内存是不是普遍紧张；
3. 当前工作盘是不是快满；
4. 现在启动训练是否合适。

因此门户里的重点应是：

1. 状态标签；
2. 简洁的百分比和剩余量；
3. 不要堆砌内部实现细节。

## 八、统一状态模型

按当前要求，状态只保留以下三类：

1. `可训练`
2. `资源紧张`
3. `状态过期`

不再保留：

1. `不建议启动大任务`

### 1. 可训练

判定建议：

至少一台服务器满足：

1. CPU 非红；
2. 内存非红；
3. 关键存储非红；
4. 至少存在空闲 GPU。

### 2. 资源紧张

判定建议：

仍有服务器可以使用，但出现以下任一情况：

1. 空闲 GPU 很少；
2. CPU 偏高；
3. 内存偏高；
4. 存储接近紧张阈值。

这类状态意味着：

1. 还能训练；
2. 但应提醒用户当前不是很宽松的资源窗口。

### 3. 状态过期

判定建议：

最近采样时间超过阈值，例如：

1. 超过 `30s` 标记过期；
2. 超过 `60s` 可在实现中进一步视作不可参考。

门户和后台都应把“过期”明确显示出来，避免用户把旧数据当实时数据。

## 九、阈值建议

建议统一三色：

### 1. CPU

1. 绿：`< 65%`
2. 黄：`65% ~ 85%`
3. 红：`> 85%`

补充条件：

1. 若 `load1 / cpu_cores > 1.0`，则至少标黄。

### 2. 内存

1. 绿：`< 75%`
2. 黄：`75% ~ 90%`
3. 红：`> 90%`

### 3. GPU

单卡近似空闲建议定义为：

1. `util < 15%`
2. 且 `显存占用 < 20%`

单卡繁忙建议定义为：

1. `util > 60%`
2. 或 `显存占用 > 60%`

单卡高压建议定义为：

1. `util > 90%`
2. 或 `显存占用 > 90%`

### 4. 存储

按使用率建议定义：

1. 绿：剩余 `> 20%`
2. 黄：剩余 `10% ~ 20%`
3. 红：剩余 `< 10%`

建议再增加绝对剩余量判断：

1. Docker 根目录剩余 `< 100GB` 至少标黄；
2. Docker 根目录剩余 `< 50GB` 直接标红。

## 十一、Agent 实现建议

第一版建议尽量不引入新依赖。

可直接使用：

1. `os.getloadavg()`
2. `/proc/meminfo`
3. `/proc/stat`
4. `shutil.disk_usage()`
5. 当前已有 `collect_gpu_info()`
6. 当前已有 `collect_storage_capabilities()`

### 1. CPU 使用率

若不引入 `psutil`，可在 Agent 进程内保存上一次 `/proc/stat` 采样值，按两次差值计算 CPU 利用率。

这样做的优点：

1. 不新增依赖；
2. 足够满足仪表盘和门户展示。

### 2. 内存

建议从 `/proc/meminfo` 读取：

1. `MemTotal`
2. `MemAvailable`

由此推导：

1. `used = total - available`
2. `usage_percent`

### 3. 存储

建议采样：

1. Docker 根目录所在文件系统；
2. 注册挂载根目录所在文件系统；
3. 去重后返回。

### 4. GPU

建议复用当前 `collect_gpu_info()` 返回的每卡：

1. 利用率；
2. 显存已用；
3. 显存总量；
4. 设备名称。

然后在 Agent 侧直接汇总：

1. `device_count`
2. `active_device_count`
3. `used_memory_bytes`
4. `total_memory_bytes`
5. `avg_util_percent`

## 十二、中心面板实现建议

### 1. 不走页面现查

不建议每次打开仪表盘或门户时同步去轮询所有 Agent。

### 2. 建议后台统一采样

建议中心面板新增一个后台线程：

1. 每 `10s` 轮询一次所有服务器 `/host/status`
2. 结果保存到中心进程内存缓存
3. 缓存同时附带 `sampled_at`
4. 后台与门户统一读取这份缓存

### 3. 建议新增中心接口

建议新增：

1. `GET /api/server-runtime-summary`
   - 给后台管理端使用
2. `GET /portal-api/runtime/<token>`
   - 给 GPU 门户使用

其中门户接口应只返回脱敏后的服务器摘要，不返回内部敏感信息。

## 十三、门户展示边界

门户建议只展示：

1. 服务器别名
2. CPU / 内存 / GPU / 存储摘要
3. 状态标签
4. 最近采样时间

门户不建议展示：

1. 宿主机 IP
2. 挂载根目录真实路径
3. Docker 根目录真实路径
4. 其他用户容器名
5. 容器级别进程信息
6. GPU UUID / PID

## 十四、页面交互建议

### 1. 管理端仪表盘

新增卡片区：

1. 每台服务器独立卡片
2. 支持颜色变化
3. 支持点击跳转到服务器页
4. 卡片内部使用圆形模块视图，不再采用左侧文本堆叠
5. GPU 较多时默认折叠，支持在当前卡片内展开全部 GPU

### 2. 服务器管理页

新增 `运行状态` 列：

1. 桌面端显示圆形模块摘要
2. 移动端放进服务器卡片中
3. GPU 默认折叠为 `+N GPU`，点击后展开当前服务器的全部 GPU
4. 展开状态按服务器单独记录，页面刷新后允许恢复为默认折叠

### 3. GPU 门户

在现有配额概览下方新增：

1. `当前训练环境参考`
2. 默认只显示简洁圆形模块卡片
3. 多 GPU 服务器默认折叠，支持用户按服务器展开全部 GPU
4. 状态标签使用固定宽度单行 badge，避免 `资源紧张` 被挤成两行

保持门户是一个：

1. 只读页面
2. 低认知负担页面
3. 用户能快速判断是否开训的页面

## 十五、建议实施顺序

建议按以下顺序实施：

### 1. Agent 运行态采样

完成：

1. `/host/status`
2. CPU / 内存 / 存储 / GPU 汇总

### 2. 中心面板缓存层

完成：

1. 后台统一采样线程
2. 内存缓存
3. 过期判定

### 3. 管理端展示

完成：

1. 仪表盘服务器运行状态卡片
2. 服务器管理页运行状态列
3. 颜色规则与状态标签

### 4. GPU 门户展示

完成：

1. 门户训练参考区块
2. 门户脱敏输出
3. 状态与采样时间展示

## 十六、结论

这项需求的关键不是“再多显示几个指标”，而是要把：

1. 静态能力检查；
2. 动态运行状态；
3. 用户训练参考；

三者彻底分开。

第一版最合理的落地方式是：

1. Agent 新增主机运行态接口；
2. 中心面板统一采样并缓存；
3. 后台展示全量状态；
4. 门户展示裁剪后的训练参考状态。

这样既能帮助管理员调度，也能帮助普通用户在启动训练前做基本判断。
