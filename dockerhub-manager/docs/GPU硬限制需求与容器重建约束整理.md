# GPU硬限制需求与容器重建约束整理

> 本文档用于整理当前 GPU 使用约束相关的需求、现状与问题，不涉及代码修改。

## 一、需求整理

当前新增诉求可以归纳为以下几点：

1. GPU 默认仍保持共享，不做独占。
2. 希望按用户设置“最多可使用 N 张 GPU”的上限。
3. 希望这个上限尽量是硬限制，而不是只在界面上告警。
4. 不希望为了 GPU 分配再拆出大量“任务容器”或“临时运行容器”。
5. 用户仍希望主要在现有容器内直接登录、直接运行程序，而不是每次运行前都走一套额外调度流程。
6. 若后续需要调整某个容器可见的 GPU 集合，希望代价尽量小，不要频繁产生大体积临时镜像。

## 二、当前现状

结合当前项目实现与已完成阶段，现状如下：

### 1. 当前 GPU 模式是“共享 + 创建时指定可见设备”

- 创建容器时可选择是否启用 GPU。
- 启用 GPU 后，当前默认行为是“自动全选该服务器全部 GPU”。
- 同一张 GPU 可以被多个容器共享访问。

这符合当前“共享 GPU”方向，但不等于“按用户硬限制最多 N 张卡”。

### 2. GPU 可见性不是运行时热更新项

当前项目里：

- `CPU / 内存 / PIDs` 可以在线更新；
- `GPU 可见设备集合` 不属于在线更新项；
- 如需修改 GPU 配置，需要走“重建容器”。

原因不是本项目实现限制，而是 Docker/NVIDIA 容器运行方式本身决定的：

- GPU 可见性在容器创建时确定；
- `docker start` 不能修改 `--gpus`；
- `docker update` 也不能把容器的可见 GPU 从一组改成另一组。

### 3. 当前用户使用方式偏向“长驻单容器”

当前更接近下面这种模式：

- 给用户分配一个可登录的长驻容器；
- 用户通过 SSH 进入这个容器；
- 在同一个容器里直接运行训练、推理、脚本等 GPU 程序。

这种模式的优点是简单，但它与“严格 GPU 张数限制且可随时变更”天然存在冲突。

### 4. 当前重建流程默认会创建临时快照镜像

现有重建逻辑支持两种来源：

1. 当前容器临时快照；
2. 已有手动备份镜像。

其中默认来源是“当前容器临时快照”。也就是说，如果直接按当前默认重建路径执行，Agent 会先：

1. 对当前容器执行一次 `docker commit`；
2. 生成类似 `dockerhub-temp/<container>:<timestamp>` 的临时镜像；
3. 再基于这个临时镜像重建容器。

因此，**如果继续沿用当前默认重建路径，那么每次因 GPU 配置变化而重建时，通常都会产生一次临时快照镜像**。

## 三、关键技术事实

### 1. 在“容器默认可见全部 GPU”的前提下，无法可靠实现按 N 张卡的硬拦截

如果容器已经能看到全部 GPU，那么宿主机无法稳定做到：

- 允许程序先使用前 `N` 张；
- 当它准备去碰第 `N+1` 张卡时，再精确拒绝这一次访问；
- 同时不影响该进程对前 `N` 张卡的已有使用。

原因在于：

- 宿主机常规能控制的是“容器启动时哪些 GPU 可见”；
- 不是“程序运行过程中第几次打开哪张 GPU 设备”；
- 很多 CUDA 框架还会在启动阶段一次性枚举或初始化所有可见 GPU。

结论：

- 若保持“默认全卡可见”，只能做软控制、告警、拒绝后续新分配、或超限后杀进程/停容器；
- 不能优雅地做成“第 `N+1` 张 GPU 自动拒绝，但前 `N` 张继续正常使用”的硬限制。

### 2. 真正的硬限制只能在容器创建前确定 GPU 集合

如果要严格控制“这个容器最多只能看到 `N` 张 GPU”，必须在容器创建时就只暴露那 `N` 张。

这意味着：

- 硬限制的控制点在“建容器”；
- 不在“容器内程序已经跑起来之后”。

### 3. 更改 GPU 分配，本质上是“重建容器实例”，不是“重建镜像”

需要区分两个层次：

- **容器实例重建**：通常是必须的；
- **镜像重新构建**：并不是必须的。

更准确地说：

- 若只是变更 GPU 集合，通常需要重新创建容器实例；
- 但不需要重新 `docker build` 基础镜像。

### 4. `docker commit` 的代价主要取决于容器可写层改动

临时快照并不是把基础镜像所有层重新复制一遍，它主要保存：

- 当前容器相对基础镜像产生的可写层改动；
- 少量镜像元数据。

因此它的代价取决于：

- 用户是否在容器里大量 `apt install`、`pip install`、下载模型、改系统文件；
- 这些改动是否都落在容器可写层里；
- 是否把真正的大数据放在挂载目录或 volume 中。

如果用户习惯是：

- 环境经常直接装在容器里；
- 大量文件写在容器系统层里；

那么频繁做临时快照，确实会带来：

- 额外写盘；
- 镜像堆积；
- 重建时间增长；
- 存储占用增加。

## 四、当前矛盾点

现在的核心矛盾不是单一实现问题，而是目标之间存在冲突：

### 1. 想要“严格 N 卡限制”

这要求平台在容器创建前就确定 GPU 可见集合。

### 2. 想要“用户继续在单个长驻容器里直接跑程序”

这意味着用户随时可在该容器内启动任意 GPU 程序，不经过额外平台调度点。

### 3. 想要“GPU 分配变更代价很低”

但严格 GPU 限制一旦变更，就需要重新创建容器实例；如果还要保留当前容器系统层改动，往往就会触发临时快照。

### 4. 想要“不拆出太多任务容器”

这排除了“开发容器 + 任务容器”的常见做法，但也意味着平台少了一个天然的 GPU 硬限制落点。

## 五、目前可以明确的结论

### 1. 若要求硬限制，更改 GPU 分配时通常需要重建容器

这个结论目前不能绕开。

更准确地说：

- 不是必须重新构建镜像；
- 但通常必须重新创建容器实例。

### 2. 当前默认重建路径下，GPU 调整通常会触发一次临时 `commit`

因为当前默认重建来源是“临时快照”。

所以如果用户希望：

- 保留当前容器中已经发生的系统层改动；
- 又要修改 GPU 可见设备；

那么当前默认路径通常就是：

- 先 `docker commit`；
- 再重建。

### 3. 这类 `commit` 不一定非常浪费，但在“脏容器”场景下会越来越重

如果容器可写层很小，临时快照成本通常还能接受。

如果容器可写层很重，例如：

- 直接在容器内装了大量依赖；
- 模型、缓存、环境文件大量写在系统层；

那么频繁调整 GPU 分配就会越来越重。

## 六、当前问题清单

基于上面的需求与现状，当前真正需要面对的问题是：

1. 是否接受“GPU 硬限制必须通过重建容器生效”这一基本事实。
2. 是否接受“当前默认重建路径会生成一次临时快照镜像”。
3. 是否要把“保留容器系统层改动”和“快速改 GPU”拆成两种不同操作。
4. 是否要进一步约束用户使用方式，例如：
   - 环境尽量做进镜像；
   - 大文件尽量写入挂载目录；
   - 减少必须依赖临时 `commit` 的场景。
5. 是否继续坚持“只保留一个长驻容器”的模型；如果坚持，则应接受 GPU 硬限制变更无法做到真正轻量。

## 七、建议作为后续设计讨论的边界

后续若继续设计 GPU 硬限制，建议先把下面几点视为固定边界：

1. **不把“运行中精确拦截第 `N+1` 张卡”作为目标**  
   这个目标在当前共享容器模式下不现实。

2. **把“GPU 集合在容器创建时确定”作为硬前提**  
   后续所有设计都基于这个事实展开。

3. **把“是否保留容器可写层改动”单独拿出来决策**  
   因为这直接决定重建时是否需要临时快照。

4. **把“容器数量控制”作为明确约束写入后续方案**  
   即后续如有新方案，也不能演化成大量任务容器泛滥的模式。

## 八、和当前项目实现的直接关系

这份整理对应当前项目中的既有事实：

- GPU 默认共享；
- 启用 GPU 时默认全选全部 GPU；
- GPU 变更不走在线更新；
- 重建支持“临时快照”与“手动备份镜像”两类来源；
- 当前默认重建来源是临时快照；
- 临时快照镜像可能在新容器仍引用它时暂时保留，不能立即删除。

因此，这不是单一 bug，而是当前产品目标、Docker 运行边界和用户使用习惯叠加后的结构性问题。
