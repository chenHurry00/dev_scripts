# 容器高级运行参数与端口分配方案

> 本文档用于整理容器高级运行参数与额外宿主机端口分配需求，仅输出方案，不修改代码。

## 一、范围收敛

本次不做模板，不开放原始 Docker 参数输入框，只支持以下 5 类高级运行参数：

1. `shm_size`
2. `ipc_mode`
3. `network_mode`
4. `ulimits`
5. `cap_add`

同时新增一项能力：

6. 容器除 SSH 外，默认额外分配 5 个宿主机暴露端口

## 二、现状

当前项目里，容器创建链路已经是结构化方式：

- 中心面板前端提交 JSON；
- 中心面板后端转发给 Agent；
- Agent 组装 `docker run`；
- 容器记录保存到中心面板。

当前 SSH 端口池为：

- `32000-32999`

当前实现中，`app.py` 与 `agent.py` 都把这整段范围视为 SSH 分配池。

如果要支持“额外暴露端口”，必须先把端口池从逻辑上拆开，而不是继续混在一个池子里。

## 三、目标

目标很明确：

1. 让容器支持少量常用高级运行参数；
2. 保持结构化配置、可回显、可重建；
3. 不做自由文本参数透传；
4. 除 SSH 外，为每个容器默认提供 5 个额外宿主机端口；
5. 端口池清晰分区，避免 SSH 与业务暴露端口相互冲突。

## 四、为什么仍然不建议开放原始参数输入框

即使这次范围已经缩小，也不建议让用户手填：

```text
--ipc=host --network=host --shm-size=16g
```

原因仍然成立：

1. 前端无法稳定校验；
2. 后端难以回显与编辑；
3. 重建时容易漏参数；
4. `network_mode=host` 会直接和现有端口映射逻辑冲突；
5. 后续若要扩展，结构化字段明显更稳。

所以本次仍建议：**只做结构化字段，不做原始参数透传。**

## 五、高级运行参数建议模型

建议在容器记录与前后端创建请求中新增：

```json
{
  "runtime_options": {
    "shm_size": "16g",
    "ipc_mode": "private",
    "network_mode": "bridge",
    "ulimits": {
      "memlock": "-1",
      "stack": "67108864",
      "nofile": "1048576"
    },
    "cap_add": ["SYS_PTRACE"]
  }
}
```

说明：

- `runtime_options` 只保存本次明确支持的 5 类参数；
- 不引入模板字段；
- 不引入额外的原始 CLI 文本字段。

## 六、5 类参数的约束建议

### 1. `shm_size`

建议：

- 允许为空；
- 支持值如 `2g`、`8g`、`16g`、`32g`；
- 后端与 Agent 都做格式校验。

用途：

- 训练任务；
- 多进程 DataLoader；
- 共享内存敏感程序。

这是最常见、最应该优先支持的一项。

### 2. `ipc_mode`

建议支持：

- `private`
- `host`

默认：

- `private`

说明：

- 很多场景只需要更大的 `/dev/shm`，并不一定需要 `ipc=host`；
- 因此页面上应提示：优先考虑 `shm_size`。

### 3. `network_mode`

建议支持：

- `bridge`
- `host`
- `none`

默认：

- `bridge`

注意：

- 这是最敏感的一项，因为它直接影响端口映射逻辑；
- `host` 模式必须做显著提示；
- `host` 模式下不再适用当前“自动分配宿主机端口映射”的默认行为。

### 4. `ulimits`

首批建议仅支持：

- `memlock`
- `stack`
- `nofile`

原因：

- 这三个最常见；
- 结构简单；
- 容易校验；
- 足够覆盖大多数真实场景。

### 5. `cap_add`

首批建议白名单仅支持：

- `SYS_PTRACE`

原因：

- 这是调试类场景最常见的附加 capability；
- 风险可控；
- 不建议第一步就开放任意 capability。

## 七、端口池重新划分建议

按你的要求，建议明确拆成两段：

### 1. SSH 端口池

- `32000-32199`

用途：

- 只用于容器 SSH 登录端口映射。

### 2. 业务暴露端口池

- `32200-32999`

用途：

- 用于容器额外对外暴露的业务端口。

这样做的好处：

1. SSH 与业务端口不会混用；
2. 更容易排查冲突；
3. 后续界面展示更清晰；
4. 便于运维做防火墙分组说明。

## 八、每容器默认额外分配 5 个端口的建议

### 1. 分配对象

除 SSH 外，每个容器默认再分配 5 个宿主机端口。

例如：

- SSH：`32005`
- 业务端口：`32240-32244`

### 2. “分配端口”与“容器内监听端口”要分开

这里要区分两层：

1. 宿主机端口
2. 容器内端口

默认分配 5 个宿主机端口，只表示这些端口被该容器预留和映射使用。  
它不代表容器内一定已经有 5 个固定服务在监听。

因此更合理的模型是：

```json
{
  "extra_port_bindings": [
    {"host_port": 32240, "container_port": 8000, "protocol": "tcp"},
    {"host_port": 32241, "container_port": 8001, "protocol": "tcp"},
    {"host_port": 32242, "container_port": 8002, "protocol": "tcp"},
    {"host_port": 32243, "container_port": 8003, "protocol": "tcp"},
    {"host_port": 32244, "container_port": 8004, "protocol": "tcp"}
  ]
}
```

其中：

- `host_port` 由平台自动分配；
- `container_port` 可给默认值，也可允许用户修改；
- `protocol` 第一版先只支持 `tcp`。

## 九、默认端口映射策略建议

建议第一版采用固定且简单的策略：

### 1. 默认给 5 条映射位

默认提供 5 个映射槽位：

1. `host_port -> 8000/tcp`
2. `host_port -> 8001/tcp`
3. `host_port -> 8002/tcp`
4. `host_port -> 8003/tcp`
5. `host_port -> 8004/tcp`

优点：

- 简单；
- 容易理解；
- 容器内常见服务端口也大多落在这个范围附近；
- 前端不用让用户从零填写。

### 2. 允许用户按需改容器内端口

例如某个容器实际上需要：

- Jupyter `8888`
- TensorBoard `6006`
- Gradio `7860`

则可以把默认槽位改成：

```json
[
  {"host_port": 32240, "container_port": 8888, "protocol": "tcp"},
  {"host_port": 32241, "container_port": 6006, "protocol": "tcp"},
  {"host_port": 32242, "container_port": 7860, "protocol": "tcp"},
  {"host_port": 32243, "container_port": 9000, "protocol": "tcp"},
  {"host_port": 32244, "container_port": 9001, "protocol": "tcp"}
]
```

### 3. 默认不支持 UDP

第一版建议只支持 `tcp`。

原因：

- 大多数日常需要都是 HTTP / HTTPS / SSH / WebSocket / Jupyter / TensorBoard；
- UDP 会额外增加校验与展示复杂度；
- 暂时不是高频需求。

## 十、端口分配规则建议

### 1. 自动分配

创建容器时：

- SSH 从 `32000-32199` 选一个空闲端口；
- 额外暴露端口从 `32200-32999` 选连续或离散的 5 个空闲端口。

### 2. 建议优先连续分配

例如优先给：

- `32240,32241,32242,32243,32244`

好处：

- 管理员和用户都更容易记；
- 界面展示更整齐；
- 对“一个容器一组端口”的认知更直观。

### 3. 连续 5 个端口找不到时

建议处理方式：

1. 先尝试找连续 5 个；
2. 找不到时，再退化为离散 5 个；
3. 如果总可用端口不足 5 个，则创建失败并给出明确提示。

这个策略兼顾体验和资源利用率。

## 十一、`network_mode=host` 与端口池的关系

这点必须说明白。

如果容器使用：

```text
network_mode=host
```

那么：

- 容器直接使用宿主机网络栈；
- `-p host:container` 这套端口映射逻辑不再是当前主要路径；
- “自动分配 5 个额外宿主机暴露端口”这一能力也就失去意义。

因此建议：

### 规则一

当 `network_mode=host` 时：

- 不自动分配额外 5 个暴露端口；
- 不使用默认 SSH 端口映射池；
- 页面必须明确提示“Host 网络模式不走自动端口映射”。

### 规则二

第一版里，`network_mode=host` 建议只用于特殊服务容器，不作为普通 SSH 分配容器常态。

### 规则三

如果用户既要 `host network`，又要 SSH 登录，则应单独设计该容器内 `sshd` 监听端口和宿主机冲突控制。  
这不建议纳入本次第一版范围。

结论：

**第一版中，`network_mode=host` 与“自动 SSH 端口 + 自动 5 个业务端口”视为互斥。**

## 十二、前端交互建议

创建容器界面新增一块：

```text
高级运行参数与端口
```

包含：

1. `shm_size`
2. `ipc_mode`
3. `network_mode`
4. `ulimits`
5. `cap_add`
6. 额外暴露端口列表

### 端口区域建议

页面上直接显示：

- SSH 端口
- 额外 5 个宿主机端口
- 每个宿主机端口对应的容器内端口

示例展示：

```text
SSH:
32005 -> 22

额外端口:
32240 -> 8888
32241 -> 6006
32242 -> 7860
32243 -> 8000
32244 -> 8001
```

### 交互原则

1. 宿主机端口默认自动分配；
2. 容器内端口允许修改；
3. 第一版不建议开放宿主机端口手工填写；
4. `network_mode=host` 时，端口区域整体禁用并提示原因。

## 十三、后端与 Agent 建议

### 中心面板后端

新增职责：

1. 维护两段端口池逻辑；
2. 自动为容器分配 1 个 SSH 端口；
3. 自动为容器分配 5 个业务宿主机端口；
4. 保存端口映射关系到容器记录；
5. 保存 `runtime_options` 到容器记录。

### Agent

新增职责：

1. 校验 `runtime_options`；
2. 组装：
   - `--shm-size`
   - `--ipc`
   - `--network`
   - `--ulimit`
   - `--cap-add`
3. 组装额外 `-p host_port:container_port` 映射；
4. 在容器详情里回传实际端口映射。

## 十四、数据保存建议

容器记录建议新增两块：

```json
{
  "runtime_options": {
    "shm_size": "16g",
    "ipc_mode": "private",
    "network_mode": "bridge",
    "ulimits": {
      "memlock": "-1",
      "stack": "67108864",
      "nofile": "1048576"
    },
    "cap_add": ["SYS_PTRACE"]
  },
  "extra_port_bindings": [
    {"host_port": 32240, "container_port": 8888, "protocol": "tcp"},
    {"host_port": 32241, "container_port": 6006, "protocol": "tcp"},
    {"host_port": 32242, "container_port": 7860, "protocol": "tcp"},
    {"host_port": 32243, "container_port": 8000, "protocol": "tcp"},
    {"host_port": 32244, "container_port": 8001, "protocol": "tcp"}
  ]
}
```

说明：

- `runtime_options` 用于记录高级运行参数；
- `extra_port_bindings` 用于记录额外业务端口映射；
- 不再引入模板类字段。

## 十五、与编辑、重建的关系

### 1. 在线修改与重建边界

以下项建议视为“修改后需要重建生效”：

1. `shm_size`
2. `ipc_mode`
3. `network_mode`
4. `cap_add`
5. 额外端口映射

`ulimits` 也建议第一版统一按“需要重建”处理，不做在线热更新。

这样边界最清晰。

### 2. 重建时要求

无论是：

- 当前容器临时快照重建；
- 已备份镜像重建；

都应保留：

1. `runtime_options`
2. `ssh_port`
3. `extra_port_bindings`

不能出现重建后端口丢失或运行参数丢失。

## 十六、权限边界建议

本次范围内，建议这样分：

### 普通可开放

1. `shm_size`
2. `ipc_mode`
3. `ulimits`

### 强提醒或管理员优先

1. `network_mode=host`
2. `cap_add`

原因：

- `network_mode=host` 会改变整个网络隔离模型；
- `cap_add` 虽然只先开 `SYS_PTRACE`，但仍属于能力扩展项。

## 十七、最简实施顺序

建议直接按这三步做：

### 第一步：数据模型与端口池拆分

目标：

1. SSH 端口池改为 `32000-32199`
2. 业务端口池改为 `32200-32999`
3. 容器记录新增 `runtime_options`
4. 容器记录新增 `extra_port_bindings`

### 第二步：创建链路支持

目标：

1. 前端创建表单支持 5 类高级参数
2. 前端显示默认 5 个额外端口槽位
3. 后端自动分配 SSH 与业务端口
4. Agent 正确拼接 Docker 参数与 `-p`

### 第三步：编辑与重建支持

目标：

1. 编辑卡片可回显上述配置
2. 修改后按“需要重建”处理
3. 快照重建和备份镜像重建保留这些配置

## 十八、最终建议

最合适的优化方案是：

1. 不做模板；
2. 不开放原始 Docker 参数文本框；
3. 只结构化支持：
   - `shm_size`
   - `ipc_mode`
   - `network_mode`
   - `ulimits`
   - `cap_add`
4. SSH 与业务暴露端口池彻底拆分：
   - SSH：`32000-32199`
   - 业务端口：`32200-32999`
5. 默认每个容器在 SSH 之外再自动分配 5 个业务宿主机端口；
6. `network_mode=host` 与自动端口映射视为互斥。

这套方案已经足够覆盖你现在提到的大多数实际需求，同时不会把系统复杂度拉得太高。
