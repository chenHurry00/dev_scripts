# DockerHub Manager 移动端界面适配方案

## 一、背景

当前中心面板在电脑端可用，但在手机端会出现以下问题：

1. 侧边栏固定宽度，占用过多横向空间
2. 顶部信息区域内容过多，小屏下挤压严重
3. 多列表格在手机端被压扁，信息难以阅读
4. 弹窗宽度和表单布局更偏向桌面端，手机上操作不顺手
5. 页面整体采用桌面管理面板布局，缺少小屏专门的降级展示

因此移动端适配不应只是缩小字体，而应做“布局降级”和“交互切换”。

## 二、目标

移动端适配目标分三层：

1. 能看
   在手机上不出现严重错位、挤压、裁切
2. 能用
   核心功能如查看容器、查看服务器、分配容器、修改资源可以完成
3. 不破坏桌面端
   桌面布局保持现有风格和效率，不因移动端适配而明显退化

## 三、适配原则

### 1. 不强行保留桌面表格

手机端横向空间有限，容器管理、服务器管理、镜像库这类多列表格不适合继续按桌面表格展示。  
在手机端应切换为卡片式列表，减少一屏内同时展示的信息量。

### 2. 桌面端与手机端分层处理

不是所有页面都必须完全重写。应按以下原则处理：

1. 桌面端继续保留现有表格和侧栏
2. 平板端允许折叠和横向滚动
3. 手机端切换为抽屉式导航 + 卡片式内容 + 全屏弹窗

### 3. 优先保证高频页面

优先适配：

1. 容器管理
2. 服务器管理
3. 概览页
4. 资源修改 / 分配容器弹窗

镜像库、用户管理、GPU 统计可沿用同一套模式后续跟进。

## 四、当前代码结构下的主要问题

从当前前端结构看，已有少量响应式规则，但不足以覆盖手机端：

1. `sidebar` 固定宽度，适合桌面，不适合手机
2. `topbar` 内容较多，手机宽度不够
3. `table-wrap` 以桌面表格为中心设计
4. 多处 `grid-template-columns: repeat(...)` 针对桌面多列布局
5. `modal` 主要按桌面浮层设计，手机上应更接近全屏
6. 页面根级滚动策略偏桌面，手机软键盘和弹窗滚动体验会受影响

## 五、推荐断点方案

建议采用三档断点：

### 1. 桌面端：`> 1024px`

保持当前布局：

1. 左侧固定侧栏
2. 顶部完整状态栏
3. 表格为主
4. 弹窗浮层

### 2. 平板端：`761px - 1024px`

做中度收缩：

1. 侧栏允许折叠
2. 顶部信息减少
3. 统计卡片从 4 列降到 2 列
4. 表格允许横向滚动
5. 表单从多列压缩为 1-2 列

### 3. 手机端：`<= 760px`

切换为移动布局：

1. 侧栏改为抽屉
2. 顶栏只保留核心元素
3. 表格改为卡片列表
4. 弹窗改为全屏或近全屏
5. 表单全部改为单列

## 六、具体方案

### 1. 导航布局

#### 目标

解决侧栏过宽、主内容区域被挤压的问题。

#### 方案

手机端：

1. 隐藏常驻侧栏
2. 增加左上角菜单按钮
3. 点击后侧栏以抽屉方式滑出
4. 点击遮罩或切换页面后自动收起

平板端：

1. 允许折叠侧栏为窄图标栏
2. 或切换为抽屉模式

#### 预期效果

主内容在手机端可获得完整宽度，不再被固定侧栏长期占用。

### 2. 顶栏布局

#### 目标

减少小屏上顶部拥挤。

#### 方案

手机端顶栏仅保留：

1. 菜单按钮
2. 品牌名称
3. 当前用户入口

隐藏或折叠：

1. 时间
2. 在线状态摘要
3. 次级状态信息

#### 预期效果

顶部高度可控，核心操作入口仍然保留。

### 3. 概览页卡片

#### 目标

让统计卡片在手机上仍可正常阅读。

#### 方案

1. 桌面端 4 列保持不变
2. 平板端改为 2 列
3. 手机端改为 1 列
4. 缩短卡片副标题文字长度
5. 控制数字字号与内边距，避免视觉拥挤

#### 预期效果

手机端一屏可顺序浏览，不会出现卡片内容压缩变形。

### 4. 容器管理与服务器管理

#### 目标

解决多列表格在手机端不可读的问题。

#### 方案

桌面端：

1. 保持表格展示

平板端：

1. 先保留表格
2. 允许横向滚动

手机端：

1. 切换为卡片列表
2. 每张卡只展示核心字段

容器卡建议展示：

1. 容器名称
2. 使用者标识
3. 所属服务器
4. 状态
5. CPU / MEM / PIDS 核心占用
6. SSH 命令与端口摘要
7. 操作按钮

服务器卡建议展示：

1. 服务器名称
2. 地址
3. 在线状态
4. Docker / GPU 能力摘要
5. 容器数量
6. 操作按钮

次要信息通过：

1. 折叠详情
2. 展开区域
3. 单独详情弹窗

实现，不在主卡片里全部铺开。

#### 预期效果

手机端不再依赖横向滚动阅读大表，主要信息能在一张卡内完成判断。

### 5. 镜像库与用户管理

#### 目标

延续统一的移动展示模式。

#### 方案

手机端同样切换为卡片式：

1. 镜像名称 / 标签
2. 类型
3. 来源容器
4. 创建时间
5. 大小
6. 操作按钮

用户管理则展示：

1. 用户名
2. 角色
3. 创建时间
4. 操作按钮

#### 预期效果

整体交互保持一致，减少不同页面的学习成本。

### 6. 弹窗与表单

#### 目标

让分配容器、修改资源、编辑服务器等高频弹窗在手机上可操作。

#### 方案

手机端：

1. 弹窗改为全屏或近全屏
2. 标题栏固定在顶部
3. 底部操作按钮固定
4. 中间内容独立滚动
5. 所有表单改为单列
6. 多列资源设置区域改为纵向堆叠
7. 端口、GPU、挂载等明细区块允许换行和折叠

平板端：

1. 宽弹窗改窄一些
2. 多列表单改为两列以内

#### 预期效果

手机端填写表单时不会因为键盘弹起、内容过宽或按钮被挤出视区而难以操作。

### 7. 表格的过渡策略

#### 目标

降低一次性改动风险。

#### 方案

可以采用两步策略：

第一步：

1. 保留桌面表格结构
2. 在平板和手机端先支持 `overflow-x: auto`
3. 先解决“完全看不了”的问题

第二步：

1. 对容器管理和服务器管理增加移动端卡片渲染
2. 手机端直接使用卡片，不再展示原始表格

#### 预期效果

先快速止血，再逐步优化，不需要一次性重写全部页面。

## 七、推荐实施顺序

为避免一次修改过大，建议按以下顺序执行：

### 第一阶段：基础响应式止血

1. 增加移动端断点规则
2. 侧栏抽屉化
3. 顶栏精简
4. 统计卡片单列化
5. 表格容器支持横向滚动
6. 弹窗全屏化

这一步目标是：手机上不再明显错位和崩坏。

### 第二阶段：核心页面卡片化

1. 容器管理手机端卡片视图
2. 服务器管理手机端卡片视图
3. 保持桌面端仍用表格

这一步目标是：手机上可以正常浏览和操作高频页面。

### 第三阶段：剩余页面统一适配

1. 镜像库卡片视图
2. 用户管理卡片视图
3. GPU 统计详情区适配
4. 导入导出、日志等页面补齐移动样式

这一步目标是：整体体验一致。

## 八、是否建议单独做移动端页面

当前不建议单独拆一套移动端页面。

原因：

1. 页面数量已经不少
2. 单独维护两套模板成本高
3. 当前系统仍在持续加功能，双套页面容易失同步

因此更适合：

1. 共用一套 HTML
2. 通过断点切换布局
3. 对少数复杂列表增加“桌面表格 / 手机卡片”双渲染

这样能在维护成本和体验之间取得平衡。

## 九、最终建议

建议按以下思路执行：

1. 不做“纯缩放式适配”
2. 采用“桌面保留 + 手机降级”的方式
3. 手机上重点改导航、表格、弹窗三类结构
4. 优先完成容器管理和服务器管理
5. 先止血，再逐步卡片化

其中最关键的判断是：

**容器管理这类多列表页面，在手机端不应继续强行使用桌面表格。**

如果只是继续压缩列宽、缩小字体、允许换行，最终视觉和操作都会比较差。  
手机端应切换到卡片式主视图，这才是更稳定的长期方案。
