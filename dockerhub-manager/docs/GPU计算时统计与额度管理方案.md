# GPU计算时统计与额度管理方案

> 本文档用于定义“GPU计算时统计与额度管理”能力，当前阶段仅整理方案，不修改代码。

## 一、目标

在保持现有 GPU 共享模式不变的前提下，新增一套**只统计、不强制限制**的管理能力：

1. 统计每个 Docker 当前实际占用了哪些 GPU。
2. 结合 GPU 利用率、显存占用、持续时间，对“是否应计为占卡”做更合理判断。
3. 按“GPU卡时”统计用户计算时消耗，例如：
   - `2 张 GPU 使用 3 小时 = 6 GPU卡时`
4. 按用户跨服务器汇总，并支持展开查看每台服务器的明细。
5. 为每个用户设置每周基础额度，并允许管理员临时增加额度。
6. 中心面板保存相关统计数据，默认保留 30 天，且保留天数可在界面修改。

## 二、界面层级

这部分不应继续塞进“容器管理”或“服务器管理”。

建议新增一个与以下栏目同级的一级栏目：

- 容器管理
- 服务器管理
- 镜像库
- **GPU计算时**

该栏目专门负责：

- 用户 GPU 计算时统计；
- 用户额度查看与调整；
- 超额提醒；
- 统计保留周期设置；
- 历史明细查询。

### 3. 本文中的“用户”定义

本文中的“用户”默认指：

- `assigned_to`，也就是“分配给（使用者标识）”

而不是：

- `login_user`，也就是容器内登录账号

原因：

- `assigned_to` 才是业务归属字段；
- `login_user` 只是容器内技术账号；
- 配额、计算时总账、跨服务器汇总都应围绕真实使用者归属，而不是围绕容器内 Linux 用户名。

因此后续实现建议固定如下规则：

1. 配额主键：`assigned_to`
2. 跨服务器汇总主键：`assigned_to`
3. 用户内同名容器汇总键：`assigned_to + container_name`
4. `login_user` 只作为详情展示字段与排查辅助字段

仅在极少数历史脏数据里，如果 `assigned_to` 为空，才允许临时回退使用 `login_user`，但不应把它作为默认主键。

## 四、核心结论

### 1. 这套能力只做统计与提醒，不做自动拦截

本方案不再尝试：

- 运行中限制用户最多同时使用多少张 GPU；
- 超额后自动拒绝容器内程序访问更多 GPU；
- 超额后自动杀容器或杀进程。

本方案只做：

- 实时识别占卡情况；
- 累计 GPU卡时；
- 对用户额度做提醒与超额统计；
- 给管理员提供调额入口。

### 2. 统计主对象是“用户”

页面总视图按用户展示。

同一用户在多台服务器上的容器会进入同一个总账。

### 3. 同名容器的跨服务器汇总只在“同一用户”范围内进行

不能只按容器名聚合，否则不同用户都叫 `train`、`dev` 时会串账。

建议聚合键分两层：

1. 用户总账键：`assigned_to`
2. 用户内工作负载键：`container_name`

也就是：

- 先按用户汇总；
- 再在用户内部按容器名汇总；
- 最后支持继续展开到每台服务器。

## 五、统计口径

### 1. 统一使用“GPU卡时”

额度与使用量统一按 `GPU卡时` 计。

定义：

- `1 张 GPU 活跃 1 小时 = 1 GPU卡时`
- `2 张 GPU 活跃 3 小时 = 6 GPU卡时`

同一容器在同一张 GPU 上即使有多个进程，也只算该容器在该 GPU 上占用 `1` 张卡，不重复倍增。

### 2. “是否计为占卡”不能只看 GPU%

单纯低利用率，不应直接判定为有效占卡。

但如果：

- GPU 利用率不高；
- 显存却持续被该容器占用；

那也不能当作“没有占卡”，更合理的定义是：

- **活跃计算**：高概率在真正跑计算；
- **低效占用**：算占卡，但利用率偏低，需要提醒；
- **可忽略**：不计入卡时。

### 3. 建议默认判定规则

对“容器-单张 GPU”这一粒度做判断。

建议默认规则如下：

#### 进入“计时状态”

满足以下任一条件即可：

1. `container_util_percent >= 10`
2. `container_memory_used_bytes >= max(2 GiB, 该卡总显存的 10%)`

#### 判定为“低效占用”

满足：

1. 已进入计时状态；
2. `container_util_percent < 10`
3. 但显存占用仍达到上面的显存门槛

这类样本：

- 仍计入 GPU卡时；
- 但在页面中单独标记为“低效占用时”。

#### 判定为“可忽略”

同时满足：

1. `container_util_percent < 10`
2. `container_memory_used_bytes < max(2 GiB, 该卡总显存的 10%)`

则该 GPU 在该容器上的这段时间不计入卡时。

### 4. 退出活跃占用的释放窗口改为 30 秒

上一轮讨论中的“连续 10 分钟降低才退出活跃”太慢，不符合现在需求。

本方案改为：

- 退出活跃/占卡状态：**连续 30 秒**低于门槛后释放

为了支撑这个判定，建议：

- 采样周期：`10 秒`
- 释放条件：连续 `3` 个采样周期都低于门槛

这样既不会因为瞬时抖动频繁跳变，也不会像 10 分钟那样拖太久。

## 六、采样与累计方式

### 1. 采样位置

建议由**中心面板后台线程**定时从各 Agent 拉取轻量 GPU 统计快照。

不要依赖浏览器页面刷新，因为：

- 浏览器关闭后统计不能停；
- 额度统计需要持续运行；
- 用户打开哪个页面不应影响记账。

### 2. 采样接口

不建议直接长期高频轮询现有 `/containers/metrics`。

原因：

- 现有接口还会附带 CPU、内存、磁盘大小等信息；
- 其中磁盘大小查询偏重；
- 这不适合 10 秒级长期采样。

建议新增一个轻量接口，例如：

```text
GET /gpu/accounting
```

只返回 GPU 计时需要的最小字段：

- 容器 ID
- 容器名
- 容器状态
- GPU 是否启用
- 当前实际活跃的 GPU 列表
- 每张 GPU 的容器级利用率
- 每张 GPU 的容器级显存占用
- 每张 GPU 总显存
- 采样时间

### 3. 计时增量

若采样周期为 `10 秒`，则每个采样点的增量为：

```text
该采样点计入的活跃 GPU 张数 × 10 / 3600
```

例如：

- 某用户某容器在一个 10 秒采样点上活跃使用 2 张卡
- 则该采样点累计：

```text
2 × 10 / 3600 = 0.005555... GPU卡时
```

### 4. 汇总粒度

建议统计链路分两层：

1. **采样层**
   - 10 秒采样一次
   - 用于活跃/释放判定

2. **存储层**
   - 按 1 分钟桶落盘
   - 每分钟累计：
     - GPU卡时
     - 低效占用卡时
     - 平均 GPU 利用率
     - 平均显存占用率
     - 峰值活跃 GPU 数

这样可以避免把 10 秒级原始点全部永久保存，减轻中心服务器存储压力。

## 八、额度模型

### 1. 基础额度可修改

需要同时支持两层基础额度：

1. **全局默认基础额度**
   - 例如默认 `72 GPU卡时 / 周`
2. **用户级基础额度覆盖**
   - 某个用户可单独改为 `120 GPU卡时 / 周`

建议规则：

- 若用户未单独设置，则继承全局默认值；
- 若用户设置了个人基础额度，则优先使用个人值。

### 2. 临时额度按“追加额度 + 生效周数”处理

临时额度不建议做复杂优先级系统，第一版只做最直接的“追加额度”。

即管理员可以给某个用户增加一条临时额度记录：

- 追加额度：例如 `+48 GPU卡时 / 周`
- 生效周数：例如 `2 周`
- 备注：例如“毕业设计训练”

建议其含义为：

- 从当前统计周开始生效；
- 连续生效 `N` 个统计周；
- 在生效期间，每周有效总额度都增加这部分额度。

例如：

- 用户基础额度：`72`
- 临时追加额度：`+48`
- 生效周数：`2`

则：

- 本周有效额度：`120`
- 下周有效额度：`120`
- 再下一周自动恢复为 `72`

### 3. 周统计周期

建议统一使用**中心面板所在时区**的自然周。

在当前部署环境下，建议采用：

- 时区：`Asia/Shanghai`
- 周起点：每周一 `00:00`

这样管理员看到的周额度与周使用量边界明确，不会因为服务器分布不同而混乱。

## 九、数据保存与保留周期

### 1. 配置数据与统计数据分开存

建议分开处理：

#### 放在 `data.json` 的内容

- 全局默认基础额度
- 用户基础额度覆盖
- 临时额度记录
- 统计保留天数设置

这些都是低频配置，适合继续纳入现有导入导出能力。

#### 不放在 `data.json` 的内容

- 高频 GPU 计时统计
- 分钟桶聚合记录
- 用户/服务器/容器使用历史

这些数据不能继续写 `data.json`，否则会带来：

- 频繁写盘
- 文件快速膨胀
- 锁竞争增加

建议单独存到 SQLite，例如：

```text
/opt/dockerhub-manager/gpu_accounting.db
```

### 2. 默认保留 30 天

中心服务器保存的这类统计数据默认保留：

- `30 天`

### 3. 保留天数可在界面修改

在 `GPU计算时` 页面中增加“统计设置”卡片，支持修改：

- 统计保留天数

建议默认值：

- `30`

建议允许范围：

- `7` 到 `365`

### 4. 清理策略

建议由中心面板后台每天执行一次清理任务：

- 删除超过保留天数的分钟桶数据；
- 同步删除过期的中间缓存；
- 保留审计日志中的额度调整记录，不随统计数据一起删除。

## 十、依赖与安装脚本约束

这部分后续落地时，必须遵守一个明确约束：

- **如果实现需要新增依赖，不能只在开发环境手动安装，必须同步进入安装/更新脚本。**

原因：

- 该项目当前通过脚本负责中心面板与 Agent 的安装/更新；
- 如果只改代码不改脚本，现网更新后很容易出现“代码已上线、依赖未装全”的故障。

建议具体约束如下：

### 1. 面板侧新增依赖

如果中心面板新增第三方 Python 依赖，则至少要同步更新：

- [requirements.txt](/home/yuchen/scripts/dockerhub-manager/requirements.txt)
- [panel_manager.sh](/home/yuchen/scripts/dockerhub-manager/scripts/panel_manager.sh)

当前面板安装/更新流程会通过虚拟环境执行：

- `pip install -r requirements.txt`

因此：

- 面板新增依赖应优先通过 `requirements.txt` 管理；
- 不应依赖管理员手工 `pip install`。

### 2. Agent 侧新增依赖

如果 Agent 新增第三方依赖，则至少要同步更新：

- [deploy.sh](/home/yuchen/scripts/dockerhub-manager/deploy.sh)
- [panel_manager.sh](/home/yuchen/scripts/dockerhub-manager/scripts/panel_manager.sh)

原因：

- 远程 Agent 部署走 `deploy.sh`；
- 本机 Agent 安装/更新走 `panel_manager.sh` 中的本机 Agent 流程；
- 两个入口都必须覆盖，否则远程服务器与本机 Agent 的依赖状态会不一致。

### 3. 当前方案优先避免引入额外依赖

这次“GPU计算时统计与额度管理”建议优先使用现有能力和 Python 标准库完成：

- SQLite 优先使用 Python 自带 `sqlite3`
- 后台线程优先使用现有 Python 线程能力

也就是说，第一版最好不要为了这项功能额外引入：

- 新数据库驱动
- 新任务调度框架
- 新缓存中间件

这样可以降低部署面变化，减少脚本改动和升级风险。

## 十四、实现建议顺序

这里原本写成三阶段，但从实际实施成本看，拆成三段偏碎，不利于连续交付。

更合适的执行方式是**两阶段做完**：

### 1. 统计底座

- 新增轻量 GPU 计时采样接口
- 中心面板后台线程 10 秒采样
- SQLite 分钟桶落盘
- 30 秒释放窗口判定
- 加入 30 天默认保留
- 增加后台清理任务

这一阶段交付后，应当已经具备：

- 正常记账
- 按用户 / 服务器 / 容器聚合
- 自动清理过期统计数据

也就是说，先把“统计对不对、账能不能算清”解决掉。

### 2. 页面与额度

- 新增一级栏目 `GPU计算时`
- 主表按用户展示
- 支持展开到服务器与容器明细
- 增加 `按容器名` 汇总视图
- 增加全局基础额度、用户基础额度、临时额度管理
- 页面支持修改保留天数
- 增加趋势展示与超额提醒

这一阶段交付后，再把“管理员如何看、如何改、如何提醒”补完整。

## 十五、当前阶段明确不做

第一版建议明确不做以下内容：

- 不做运行中自动拦截 GPU 使用
- 不做超额后自动停容器
- 不做复杂配额调度器
- 不做多级额度优先级系统
- 不做秒级永久原始样本存档

这样范围是收敛的，且与当前系统结构兼容。

## 十六、最终建议

这条路线适合当前项目，原因很直接：

1. 不破坏现有“共享 GPU + 长驻容器”的使用方式。
2. 可以真正解决“管理员需要知道谁花了多少计算资源”的问题。
3. 不需要把问题扭成复杂调度系统。
4. 后续如果将来真要做限制，也可以基于这套统计口径继续演进，而不是推倒重来。
