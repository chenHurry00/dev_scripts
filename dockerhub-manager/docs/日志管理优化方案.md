# 日志管理优化方案

## 1. 当前现状

当前网页中的“实时日志”和“系统日志”并不是两套独立日志源，而是同一份中心面板审计日志：

- 来源接口：`/api/logs`
- 存储位置：中心面板 `data.json` 中的 `audit_logs`
- 刷新方式：前端每 10 秒轮询一次
- 现阶段保留策略：仅保留最近若干条审计记录

同时，中心面板脚本中的：

- “查看中心面板日志”
- “查看本机 Agent 日志”

实际查看的是宿主机 `journalctl` 中的 systemd 服务日志。这与网页里的审计日志不是同一类数据。

因此当前系统实际上存在三类不同语义的日志：

1. 管理操作审计日志
2. 面板 / Agent 服务运行日志
3. 业务容器运行日志

但网页界面尚未将它们清晰拆分。

## 2. 当前问题

### 2.1 日志类型混用

网页里的“实时日志”和“系统日志”都显示同一份审计日志，名称容易误导管理员。

### 2.2 保留策略过弱

如果只按很小的条数上限保留，管理员很难回看最近几天或几周的重要操作历史。

### 2.3 检索能力不足

当前缺少以下常用管理能力：

- 按用户筛选
- 按服务器筛选
- 按容器筛选
- 按动作类型筛选
- 按时间范围筛选
- 按级别筛选
- 关键词搜索

### 2.4 缺少链路追踪

一次“容器重建”“镜像拉取”“镜像删除”这类复杂操作，目前没有统一的操作 ID，面板、Agent、容器事件之间不容易串联排查。

## 3. 建议的日志结构

建议将日志明确拆成三层：

### 3.1 审计日志

用于回答：

- 谁在什么时候做了什么操作
- 操作是否成功
- 操作作用到了哪台服务器、哪个容器、哪个镜像

建议字段：

- `time`
- `level`
- `actor`
- `action`
- `server_id`
- `container_name`
- `target_type`
- `target_id`
- `result`
- `message`
- `operation_id`
- `metadata`

### 3.2 面板 / Agent 服务日志

用于回答：

- 中心面板自身为什么报错
- 某台 Agent 为什么调用失败
- 服务是否重启、异常退出、依赖失败

这部分建议继续以宿主机 `journalctl` 为主，网页只做按需读取，不建议全量复制进 `data.json`。

### 3.3 容器运行日志

用于回答：

- 业务容器内部运行为什么报错
- SSH 启动是否正常
- 程序自身是否输出异常

这部分建议保持按需读取 `docker logs`，不建议中心面板长期持久化。

## 4. 管理员最需要的优化能力

如果目标是“便于管理员进行管理”，建议优先增加以下能力：

### 4.1 页面拆分

网页日志入口建议拆成：

1. 审计日志
2. 面板日志
3. Agent 日志
4. 容器日志

不再使用“实时日志 / 系统日志”这种容易混淆的名称。

### 4.2 筛选与检索

审计日志至少支持：

- 用户
- 服务器
- 容器
- 动作类型
- 级别
- 时间范围
- 关键词

### 4.3 分页与导出

建议支持：

- 分页浏览
- 导出 CSV
- 导出 JSON
- 导出文本

### 4.4 自动刷新控制

建议支持：

- 自动刷新开关
- 暂停滚动
- 仅看错误
- 仅看最近 N 分钟

### 4.5 操作链路关联

对“容器创建 / 重建 / 删除 / 镜像拉取 / 镜像删除”这类跨组件操作，建议引入统一 `operation_id`，便于管理员按一次操作追完整条链路。

## 5. 存储策略建议

### 5.1 当前阶段

当前阶段不必立刻引入复杂日志系统，建议先做：

1. 审计日志保留上限从较小值提升到更可用的条数
2. 网页审计日志支持筛选和分页
3. 面板日志 / Agent 日志提供只读查看入口

### 5.2 下一阶段

建议把审计日志从 `data.json` 迁移到 `SQLite`：

- 查询更快
- 支持筛选分页
- 支持导出
- 不会让配置文件持续膨胀

### 5.3 不建议的做法

当前阶段不建议：

- 把所有容器日志全量同步到中心面板
- 把 `journalctl` 全量复制进配置文件
- 在 `data.json` 中长期堆积大量非结构化日志文本

这些做法会让配置文件膨胀、检索能力变差、导入导出变慢。

## 6. 本次即时调整

为了先提升可用性，当前先做一个保守调整：

- 中心面板审计日志保留上限扩大为最近 `2000` 条

说明：

- 这依然是“按条数保留”，不是“按天数保留”
- 如果系统操作频率很高，`2000` 条仍可能在较短时间内被覆盖
- 真正要解决长期检索与管理问题，仍建议后续迁移到 `SQLite`

## 7. 推荐实施顺序

建议按以下顺序推进：

1. 统一网页日志命名，拆清“审计日志 / 面板日志 / Agent 日志 / 容器日志”
2. 审计日志从 `data.json` 迁移到 `SQLite`
3. 增加筛选、分页、导出
4. 增加 `operation_id` 链路追踪
5. 再考虑更高级的日志聚合能力

这条路径改动范围可控，且能优先提升管理员实际排障效率。
