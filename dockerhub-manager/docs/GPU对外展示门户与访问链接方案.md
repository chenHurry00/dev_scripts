# GPU对外展示门户与访问链接方案

> 本文档用于定义“GPU计算时对外展示门户与访问链接”能力，当前阶段仅整理方案，不修改代码。

## 一、目标

在现有 GPU 计算时统计基础上，新增一套**对外展示门户**，同时保留管理端完整查看能力。

目标如下：

1. 管理端可以查看最近 30 天 GPU 用量排名。
2. 管理端可以查看任意业务用户最近 30 天每日用量曲线。
3. 对外提供一个单独门户页面，供业务用户查看自己的 GPU 用量。
4. 对外门户中：
   - 用户本人可看到自己的实名完整数据；
   - 其他用户的数据可看，但用户名需脱敏显示；
   - 不允许查看其他用户的详细曲线、容器明细、服务器明细。
5. 管理端每个用户都可以生成并复制专属访问链接。
6. 管理端可以一键导出访问链接表，导出格式使用 `CSV`。
7. 对外门户单独监听 `5002` 端口。

## 二、总体结构

建议保持“两套入口、同一套数据源”：

### 1. 管理端 `5000`

继续使用当前中心面板：

- 登录后查看全量 GPU 统计；
- 查看最近 30 天排名；
- 查看任意用户最近 30 天每日用量曲线；
- 管理访问链接；
- 导出访问链接表。

### 2. 对外门户 `5002`

新增一个只读门户：

- 独立页面；
- 独立端口；
- 不提供资源管理能力；
- 只提供 GPU 用量展示。

### 3. 模板组织

建议新增模板文件：

- `templates/gpu_usage_portal.html`

该模板既可：

- 独立作为 `5002` 的门户页面；
- 也可由管理端在新标签页打开，或后续通过嵌入方式复用。

## 三、访问身份设计

### 1. 访问标识口径

门户访问身份继续使用当前 GPU 统计的业务用户口径：

- `assigned_to`

不使用：

- 平台登录用户；
- 容器登录用户；
- 宿主机用户名。

这样可以保持以下能力不变：

- 同一业务用户跨服务器累计；
- 同名容器跨服务器累计；
- 与当前 GPU 计算时统计口径一致。

### 2. 专属访问 token

每个 `assigned_to` 对应一个门户访问 token。

用户通过如下形式访问：

- `http://<host>:5002/portal/<token>`

### 3. token 长度

根据当前要求，token 使用：

- **16 位随机字符串**

这样做的优点：

- 链接较短；
- 复制和发放更方便；
- 适合人工使用。

需要注意：

- 16 位 token 的安全性明显低于更长随机串；
- 因此必须保证 token 来源足够随机，不能使用可预测规则；
- 门户仍应只暴露只读数据，不能附带管理能力。

建议使用：

- 大小写字母 + 数字；
- 服务端随机生成；
- 不包含可读的用户名信息。

## 四、展示规则

### 1. 本人可见内容

在 `5002` 门户中，用户本人可看到：

- 自己的业务用户名；
- 最近 30 天每日 GPU 卡时曲线；
- 最近 7 天累计用量；
- 最近 30 天累计用量；
- 本周累计用量；
- 当前基础额度；
- 当前临时额度；
- 当前有效额度；
- 当前额度状态；
- 当前活跃 GPU 数。

### 2. 其他用户可见内容

用户还可以看到其他人的**匿名榜单**：

- 最近 30 天用量排名；
- 最近 30 天累计 GPU 卡时；
- 当前是否活跃；
- 当前活跃 GPU 数。

但这些用户必须脱敏显示，不能显示实名用户名。

### 3. 其他用户不可见内容

对外门户中，不允许看到其他人的：

- 实名用户名；
- 最近 30 天每日曲线；
- 服务器分布；
- 容器分布；
- 临时额度明细；
- 操作记录；
- 访问链接。

## 五、脱敏规则

其他用户名建议采用“保留少量特征 + 中间星号”的形式。

推荐规则：

1. 长度 `1`：
   - `*`
2. 长度 `2`：
   - `a*`
3. 长度 `3-4`：
   - `a**`
4. 长度 `>=5`：
   - 保留首尾，中间替换为 `*`
   - 例如：
     - `alice` -> `a***e`
     - `zhangsan` -> `z******n`

这样可以满足：

- 不直接暴露完整用户名；
- 排名表中仍能粗略区分不同用户。

## 六、数据层方案

当前分钟桶表已经存在：

- `gpu_accounting_minute_usage`

参考：

- [app.py](/home/yuchen/scripts/dockerhub-manager/app.py:494)

因此本需求不需要修改采样逻辑，只需要补充新的聚合查询。

### 1. 最近 30 天排名

新增查询：

- 按 `username` 聚合最近 30 天 `SUM(gpu_card_hours)`
- 按用量倒序排列

建议新增函数：

- `query_gpu_accounting_ranking_by_user(days=30)`

返回建议包含：

- `username`
- `gpu_card_hours_30d`
- `low_efficiency_card_hours_30d`
- `avg_gpu_util_percent_30d`
- `peak_active_gpu_count_30d`
- `current_active_gpu_count`

### 2. 单用户最近 30 天每日曲线

新增查询：

- 按日期聚合最近 30 天 `SUM(gpu_card_hours)`

建议新增函数：

- `query_gpu_accounting_daily_usage_for_user(username, days=30)`

返回建议包含：

- `day`
- `gpu_card_hours`
- `low_efficiency_card_hours`

### 3. 日期补零

由于并不是每天都有使用记录，因此返回给前端前应补齐最近 30 天所有日期。

也就是：

- 有数据的日期返回真实值；
- 无数据的日期返回 `0`。

否则曲线图会断裂，前端逻辑也会更复杂。

### 4. 索引优化

为支持最近 30 天排名与日曲线查询，建议补一个索引：

- `(bucket_start, username)`

当前已有：

- `(username, bucket_start)`

但最近 30 天全局排名常常先按时间窗口过滤，再按用户名聚合，因此补充时间优先索引更稳。

## 七、门户 token 数据结构

建议将门户 token 放入现有 `gpu_accounting` 配置结构中统一保存。

示意结构：

```json
{
  "gpu_accounting": {
    "portal_tokens": {
      "alice": {
        "token": "Ab12Cd34Ef56Gh78",
        "created_at": "2026-06-02T12:00:00",
        "updated_at": "2026-06-02T12:00:00",
        "created_by": "admin"
      }
    }
  }
}
```

字段建议：

- `token`
- `created_at`
- `updated_at`
- `created_by`

后续如需扩展，可再补：

- `disabled`
- `last_access_at`
- `last_access_ip`

第一阶段不建议加太多字段。

## 八、管理端功能方案

### 1. GPU 用量页面新增能力

在现有 GPU 用量页面中新增：

1. 最近 30 天排名视图
2. 最近 30 天曲线查看
3. 门户访问链接操作

### 2. 每用户新增操作

建议在用户 GPU 用量总表的操作列增加：

- `明细`
- `30天曲线`
- `复制访问链接`
- `重置链接`

其中：

- `复制访问链接`：若没有 token，则自动生成后再复制；
- `重置链接`：生成新 token，旧链接失效。

### 3. 顶部新增导出能力

建议增加按钮：

- `导出访问链接表`

导出内容使用 `CSV`，文件名建议：

- `gpu-portal-links-YYYYMMDD-HHMMSS.csv`

列建议为：

- `assigned_to`
- `portal_url`
- `token`
- `created_at`
- `updated_at`
- `created_by`

如果你希望降低泄露风险，也可以在导出时只保留：

- `assigned_to`
- `portal_url`

第一版建议直接包含 token，因为链接本身就包含 token。

## 九、对外门户页面方案

建议 `templates/gpu_usage_portal.html` 页面分为三块：

### 1. 本人概览

显示：

- 用户名（实名）
- 最近 7 天累计
- 最近 30 天累计
- 本周累计
- 当前基础额度
- 当前临时额度
- 当前有效额度
- 当前状态
- 当前活跃 GPU 数

### 2. 本人最近 30 天曲线

建议用折线图展示：

- 横轴：日期
- 纵轴：每日 GPU 卡时

必要时可附加一条低效占用曲线，但第一版不是必需。

### 3. 匿名排名榜

显示最近 30 天排名：

- 排名
- 脱敏用户名
- 最近 30 天累计用量
- 当前活跃 GPU 数

规则：

- 本人行显示实名；
- 其他行显示脱敏名；
- 不支持点击他人进一步展开。

## 十、接口建议

### 1. 管理端接口

建议新增：

- `GET /api/gpu-accounting/ranking?days=30`
- `GET /api/gpu-accounting/users/<username>/daily?days=30`
- `POST /api/gpu-accounting/users/<username>/portal-token`
  - 获取或生成 token
- `POST /api/gpu-accounting/users/<username>/portal-token/reset`
  - 重置 token
- `GET /api/gpu-accounting/portal-links/export`
  - 导出 CSV

### 2. 门户接口

建议新增只读接口：

- `GET /portal/<token>`
  - 渲染门户页面
- `GET /portal-api/me/<token>`
  - 返回本人概览与 30 天曲线
- `GET /portal-api/ranking/<token>`
  - 返回榜单，除本人外全部脱敏

注意：

- 不提供通过用户名查看其他人详情的接口；
- 不提供写接口；
- 不提供配额修改接口；
- 不提供用户列表接口。

## 十一、5002 端口与进程建议

### 1. 端口

建议新增：

- `5002` 作为 GPU 对外门户端口

### 2. 进程模式

建议与管理面板分开监听，但可以继续复用同一份 Python 代码。

更稳妥的方式是：

- 同一项目代码；
- 两个 gunicorn 进程；
- 两个 systemd 服务；
- 不同启动参数。

例如：

- `dockerhub-panel.service` -> `5000`
- `dockerhub-gpu-portal.service` -> `5002`

### 3. 原因

这样做的好处：

- 管理端与门户端边界清晰；
- 防火墙规则更容易控制；
- 后续门户单独限流、单独重启更方便；
- 不会把管理页面无意间暴露到对外端口。

## 十二、安全建议

### 1. 结论

虽然门户不需要账号密码，但**不能视为完全公开页面**。

门户安全边界应建立在：

- 专属 token
- 只读接口
- 脱敏展示

之上。

### 2. 最低要求

建议至少满足：

1. token 使用服务端随机生成；
2. 门户只读；
3. 除本人外其他用户名全部脱敏；
4. 支持重置 token；
5. 门户端不暴露管理接口；
6. 防火墙仅开放 `5002`，不额外暴露管理端。

### 3. 可选增强

后续可再增加：

- 访问频率限制；
- 访问日志；
- token 最近访问时间；
- token 最近访问 IP；
- 一键停用 token。

第一版不建议全部同时做。

## 十三、CSV 导出选择说明

当前项目未包含 Excel 相关依赖。

因此本阶段采用：

- `CSV`

而不是：

- `.xlsx`

这样做的原因：

1. 不新增 Python 依赖；
2. Excel 可直接打开 CSV；
3. 导出实现简单稳定；
4. 安装脚本无需同步增加额外包。

如果后续明确需要：

- 多 sheet；
- 样式；
- 冻结表头；
- 自动列宽；

再升级为真正的 `.xlsx` 更合适。

## 十四、实施顺序建议

建议按以下顺序实施：

1. 数据层
   - 新增 30 天排名查询
   - 新增 30 天每日曲线查询
   - 新增 portal token 保存结构
2. 管理端
   - GPU 用量页增加排名和曲线
   - 增加复制链接 / 重置链接
   - 增加导出 CSV
3. 对外门户
   - 新建 `gpu_usage_portal.html`
   - 完成本人实名 + 他人匿名榜单展示
4. 部署
   - 新增 `5002` 服务
   - 更新 `panel_manager.sh`
   - 更新 README 与放行说明

## 十五、最终边界

本方案最终边界如下：

- 管理端：
  - 可查看所有实名数据；
  - 可生成、复制、重置访问链接；
  - 可导出链接 CSV；
  - 可查看 30 天排名与任意用户 30 天曲线。

- 对外门户：
  - 用户通过专属 token 访问；
  - 可看自己实名完整数据；
  - 可看他人匿名排名数据；
  - 不可查看他人详细曲线；
  - 不可进行任何管理操作。
