# 文档站建设与图片管理方案

> 本文档用于定义 DockerHub Manager 的正式文档站建设方案。  
> 目标不是继续堆积零散 Markdown，而是建设一套可浏览、可检索、可维护、可对外访问的文档站。

## 一、背景与问题

当前仓库中的文档主要集中在 `docs/` 目录，存在以下问题：

1. 文档以研发方案、过程记录为主，不适合直接给分配员和普通用户阅读。
2. Markdown 直接查看的阅读体验较弱：
   - 没有统一导航；
   - 没有全站搜索；
   - 页面内目录能力弱；
   - 截图插入后整体版式不够像正式文档站。
3. 目前已经开始出现两类正式手册需求：
   - 分配员操作与维护手册；
   - 用户 Docker 开发使用手册。
4. 后续还会持续增加：
   - 常见问题；
   - GPU 用量说明；
   - 端口、挂载目录、镜像备份等专题说明。

因此，单纯继续往 `docs/` 中追加 Markdown 已不合适，需要建设独立的正式文档站。

## 二、建设目标

正式文档站应满足以下目标：

1. 支持左侧目录导航。
2. 支持全站搜索。
3. 支持页面内目录。
4. 支持代码块高亮、提示块、警告块、表格等文档常用能力。
5. 支持截图插入，并能较好地管理图片资源。
6. 支持通过中心服务器独立端口访问。
7. 与当前管理面板、GPU 门户分离，避免把文档逻辑继续堆进 `app.py`。
8. 保留当前 `docs/` 目录作为研发资料区，不和正式用户文档混用。

## 三、推荐技术方案

推荐采用：

- `MkDocs`
- `Material for MkDocs`

作为正式文档站方案。

这是当前最适合本项目现状的选择，原因如下：

1. 当前项目本身使用 Python、Flask、gunicorn、systemd。
2. `MkDocs` 属于 Python 工具链，容易纳入现有部署体系。
3. 正式文档站效果成熟，接近常见开源项目官网文档体验。
4. 文档源文件仍使用 Markdown，迁移成本低。
5. 不需要额外引入完整的 Node 前端工程。

不建议采用的方案：

1. 继续直接查看原始 Markdown
- 适合作为仓库内资料，不适合作为正式说明站。

2. 在现有 Flask 面板里自己写 Markdown 渲染器
- 初看简单，实际会不断追加目录、样式、搜索、图片放大、导航等需求；
- 最终会让 `app.py` 越来越臃肿；
- 成品大概率不如现成文档站方案。

## 四、推荐目录结构

建议将“研发资料”和“正式文档站”分开。

### 1. 保留当前 `docs/`

用途：

1. 研发方案
2. 实施记录
3. 架构说明
4. 历史设计文档

这部分继续保留在仓库中，不直接作为最终用户文档站内容。

### 2. 新增正式文档源目录

建议新增目录：

```text
docs-site/
  mkdocs.yml
  docs/
    index.md
    allocator/
      index.md
    user/
      index.md
    faq/
      index.md
    gpu/
      index.md
    assets/
      images/
        allocator/
        user/
        common/
```

说明：

1. `docs-site/docs/`
- 存放最终展示用的正式文档。

2. `docs-site/mkdocs.yml`
- 文档站导航、主题、插件配置文件。

3. `docs-site/docs/assets/images/`
- 存放文档截图和图示资源。

## 五、文档内容分层建议

正式文档站建议只放“最终给人看的文档”，不要把研发方案直接暴露进去。

推荐栏目如下。

### 1. 首页

建议内容：

1. 平台简介
2. 适用对象说明
3. 文档入口导航
4. 常见问题入口

### 2. 分配员手册

建议拆分为多个页面：

1. 平台概览
2. 网页端功能说明
3. 容器分配流程
4. 资源调整与重建
5. 镜像与备份管理
6. GPU 额度与巡检
7. 常见异常处理

### 3. 用户手册

建议拆分为多个页面：

1. 为什么改为 Docker 开发
2. 与宿主机开发的区别
3. 登录与基础使用
4. 挂载目录与文件传输
5. 端口映射与服务对外访问
6. GPU 使用说明
7. 常见问题

### 4. FAQ

建议把高频问题单独集中：

1. 登录不上
2. 文件找不到
3. 端口不通
4. GPU 不可见
5. 容器重建后环境变化
6. 资源不够如何申请

### 5. GPU 用量说明

建议单独说明：

1. 统计口径
2. 本周额度与临时额度
3. 30 天排行与曲线含义
4. 对外门户如何看

## 六、依赖方案

建设文档站需要新增依赖。

### 1. 推荐依赖

建议至少新增：

```text
mkdocs
mkdocs-material
pymdown-extensions
```

如果需要更好的图片查看体验，建议再增加：

```text
mkdocs-glightbox
```

### 2. 依赖管理方式

不建议把文档站依赖直接混进当前面板运行依赖。

建议新增独立依赖文件：

```text
requirements-docs.txt
```

原因：

1. 面板运行依赖应尽量保持精简。
2. 文档站插件后续可能继续增减。
3. 独立维护更清晰，不影响主面板和 Agent。

### 3. 依赖职责边界

建议：

1. `requirements.txt`
- 只给中心面板和相关运行服务使用。

2. `requirements-docs.txt`
- 只给文档站构建和文档服务使用。

## 七、端口与服务规划

建议将文档站作为独立服务部署。

### 1. 推荐端口规划

```text
5000  中心管理面板
5002  GPU 对外门户
5003  正式文档站
```

### 2. 推荐服务形式

不建议让文档站继续走 Flask 动态渲染。

建议采用：

1. Markdown 文档源
2. `mkdocs build`
3. 生成静态站点
4. 独立服务对外提供访问

这样做的优点：

1. 文档站和面板完全解耦。
2. 文档访问不会影响管理面板逻辑。
3. 样式、搜索、导航由成熟方案负责。

### 3. systemd 服务建议

建议新增独立文档服务，例如：

```text
dockerhub-docs.service
```

职责：

1. 启动文档站服务
2. 监听 `5003`
3. 读取构建后的静态文件目录

## 八、`panel_manager.sh` 更新建议

如果文档站要长期使用，管理脚本必须一并支持。

否则后续维护会分裂成：

1. 面板一套更新流程
2. 文档站一套手工流程

这会很快变乱。

### 1. 建议新增的能力

建议在 `scripts/panel_manager.sh` 中增加：

1. 安装/更新文档站
2. 重建文档站
3. 重启文档站
4. 查看文档站状态
5. 查看文档站日志
6. 文档站端口配置

### 2. 建议的配置项

例如新增：

```text
DOCS_PORT=5003
```

必要时还可增加：

```text
DOCS_PUBLIC_BASE_URL=
```

用于后续反向代理或公开访问场景。

### 3. 推荐操作方式

建议脚本安装/更新文档站时完成以下动作：

1. 安装 `requirements-docs.txt`
2. 执行 `mkdocs build`
3. 将构建产物部署到固定目录
4. 注册并启动文档服务
5. 输出访问地址提示

## 九、图片管理方案

如果正式文档站要长期维护，图片必须有统一规范。

否则很快会出现：

1. 图片乱放
2. 文件名混乱
3. 路径失效
4. 同一页面图片风格不一致

### 1. 图片目录建议

建议统一放在：

```text
docs-site/docs/assets/images/
```

再按对象拆分：

```text
docs-site/docs/assets/images/allocator/
docs-site/docs/assets/images/user/
docs-site/docs/assets/images/common/
```

### 2. 命名规范建议

建议：

1. 使用英文或拼音
2. 使用小写
3. 使用短横线分隔
4. 不使用空格
5. 不使用中文文件名

例如：

```text
allocator-create-container.png
allocator-gpu-accounting-table.png
user-port-mapping.png
user-workspace-upload.png
common-login-page.png
```

### 3. 图片格式建议

推荐：

1. 界面截图使用 `png`
2. 流程图或结构图使用 `svg`

不建议第一阶段就大量引入复杂图片格式转换流程。

先保持简单：

1. 截图用 `png`
2. 图示用 `svg`

### 4. Markdown 插图方式

建议在 Markdown 中直接相对引用：

```md
![分配容器页面](../assets/images/allocator/allocator-create-container.png)
```

### 5. 图片展示增强

如果启用 `mkdocs-glightbox`，可以获得更接近正式文档站的体验：

1. 图片点击放大
2. 更方便阅读截图细节

这对操作手册很有价值，建议启用。

## 十、文风与页面风格建议

文档站不只是“能看”，还要像正式文档。

建议统一文风：

### 1. 每页开头固定说明

建议每页开头写清：

1. 适用对象
2. 适用场景
3. 阅读前提

### 2. 先给结论，再给解释

例如：

1. “重要数据应优先放在挂载目录”
2. 然后再解释为什么

### 3. 多用提示块

建议统一使用以下块：

1. 注意
2. 建议
3. 常见误区
4. 排查步骤

### 4. FAQ 单独成页

不要把大量问答散落在正文中。

### 5. 页面长度控制

操作文档尽量拆页，不建议一个页面塞完所有内容。

## 十一、安全边界建议

文档站通常可以对内网用户开放，但不应暴露敏感信息。

### 1. 可以放的内容

1. 使用说明
2. 登录方法
3. 端口映射解释
4. 挂载目录说明
5. GPU 用量查看说明
6. 常见问题与排查建议

### 2. 不建议放的内容

1. Agent Token
2. 管理员密码相关内容
3. 宿主机敏感目录全路径细节
4. 系统恢复过程中的敏感命令
5. 可直接用于攻击面板的内部配置细节

### 3. 访问范围建议

建议至少默认限制为内网访问。

如果后续要更大范围开放，应增加：

1. 反向代理
2. HTTPS
3. 来源限制

## 十二、实施建议顺序

建议按以下顺序做，不要一次性全堆。

### 第一阶段：搭底座

1. 新建 `docs-site/`
2. 新建 `mkdocs.yml`
3. 新建 `requirements-docs.txt`
4. 迁移首页、分配员手册、用户手册、FAQ 基础结构

### 第二阶段：接入部署

1. 在 `panel_manager.sh` 中增加文档站管理命令
2. 新增文档服务
3. 新增 `5003` 端口访问
4. 更新 `README.md`

### 第三阶段：补图片与润色

1. 为关键操作页补截图
2. 为用户手册补端口、挂载目录、GPU 用量说明图
3. 统一文风
4. 调整导航结构

## 十三、最终建议结论

本项目正式文档体系建议明确分为两层：

1. `docs/`
- 继续保留为内部研发资料区

2. `docs-site/`
- 作为正式文档站源目录

推荐技术方案：

1. `MkDocs`
2. `Material for MkDocs`
3. 独立依赖文件 `requirements-docs.txt`
4. 独立端口 `5003`
5. 独立服务 `dockerhub-docs.service`

推荐图片策略：

1. 图片统一放到 `docs-site/docs/assets/images/`
2. 按 `allocator / user / common` 分目录
3. 截图优先 `png`
4. 图示优先 `svg`
5. 启用图片点击放大插件

这是当前最适合该项目的文档建设方式，兼顾：

1. 展示效果
2. 维护成本
3. 部署一致性
4. 与现有 Python 技术栈的兼容性
