# 用户手册

## 适用范围

本手册面向通过平台获得 Docker 容器资源的普通用户，涵盖开发、训练、调试及服务部署等场景。

## 容器分配信息说明

用户在获得容器资源后，分配员将通过容器管理界面提供以下配置信息：

- SSH 登录命令及端口
- 容器用户账号标识
- 身份验证方式（密码或公钥）
- 业务端口映射规则
- 计算资源配额（CPU、内存、磁盘、GPU）

## 容器环境说明

与传统宿主机直接开发不同，平台当前分配的资源包括：

- 独立容器实例
- 容器登录账号
- SSH 登录端口
- 若干业务映射端口
- 挂载目录
- GPU 使用权限（按需分配）

用户应理解以下要点：

1. 当前操作环境为容器内部，而非宿主机系统
2. 资源（CPU、内存、GPU）及端口使用均受平台管控
3. 容器内可安装依赖并运行程序，但需遵循资源配额限制

## 与宿主机开发的差异

### 操作环境隔离

容器内操作仅影响当前容器实例，不应将宿主机视为个人开发环境进行修改。

### 数据持久化要求

容器实例可能被重建，容器系统层（非挂载目录）中的数据存在丢失风险。

!!! warning "数据存储原则"
    代码、模型、数据集及实验结果应优先存储在挂载目录中，以避免容器重建导致的数据丢失。

### 端口映射机制

对外服务必须通过映射端口访问，用户需：

1. 确认分配的业务端口映射规则
2. 在容器内监听对应的容器端口
3. 通过宿主机映射端口对外提供服务

### GPU 使用统计

平台对 GPU 使用进行实时统计，包括：

- 占用的 GPU 设备编号
- 使用时长
- GPU 利用率及显存占用情况

不建议长期空占、低利用率占用 GPU 或任务结束后未清理进程。

## 容器登录

分配员提供的登录信息通常包括：

- SSH 登录命令
- 登录用户名
- 身份验证方式（密码或公钥）
- 业务端口映射规则

典型登录命令示例：

```bash
ssh -p 32000 youruser@server-ip
```

登录后建议确认当前环境：

```bash
whoami
hostname
pwd
```

通常情况下，`hostname` 显示为容器名或容器 ID，确认当前环境为容器内部。

若分配员提供密码登录方式，该密码对应容器内的登录用户；修改密码后，后续 SSH 登录将使用新密码。

## 容器能力限制

以下能力在容器分配时由分配员配置，无法在容器内临时开启：

- GPU 分配状态
- 额外业务端口数量
- 可写层磁盘上限
- `shm_size`、`ipc_mode`、`network_mode` 等运行参数
- `ulimits`、`cap_add` 等高级配置

若遇到服务启动失败、共享内存不足、端口不足或 GPU 不可见等问题，应联系分配员调整容器参数，而非尝试在容器内修复。

## 挂载目录使用

分配员通常将宿主机某个目录挂载至容器内（例如 `/workspace`），建议将以下内容优先存储在挂载目录：

- 项目代码
- 数据集
- 模型权重
- 日志与输出结果

**优势**

- 容器重建后数据仍可保留
- 不受容器系统层变化影响

## 文件传输

推荐流程：

1. 将文件传输至挂载目录
2. 登录容器确认文件可见性

传输完成后建议执行检查：

```bash
cd /workspace
ls
du -sh .
```

若文件已存在于挂载目录，容器内通常可直接访问。

## 对外服务部署

若在容器内启动以下服务：

- Web 应用
- API 服务
- Jupyter Notebook
- Gradio 应用
- TensorBoard

需理解端口映射规则。例如分配员提供的映射规则为：

```text
server-ip:32200 -> container:8000/tcp
server-ip:32201 -> container:8001/tcp
```

表示：

- 容器内监听 `8000` 端口
- 外部通过宿主机 `32200` 端口访问

示例：

```bash
python -m http.server 8000 --bind 0.0.0.0
```

外部访问地址为：

```text
http://server-ip:32200
```

!!! tip "监听地址配置"
    服务应监听 `0.0.0.0`，若仅监听 `127.0.0.1`，外部通常无法访问。

## 端口映射解读

容器管理页面直接显示端口映射规则，用户需按以下方式理解：

- 左侧为宿主机对外端口
- 右侧为容器内服务端口
- 外部访问始终通过宿主机端口

例如映射规则显示：

```text
32210 -> 8000/tcp
32211 -> 7860/tcp
```

表示：

- Web 服务可监听容器内 `8000` 端口
- Gradio 或其他服务可监听容器内 `7860` 端口
- 服务是否可对外访问取决于容器内是否已启动并监听对应端口

## 资源限制理解

容器可能被设置以下限制：

- CPU 上限
- 内存上限
- PIDs 上限
- 可写层磁盘上限
- GPU 权限

用户不应默认拥有宿主机全部资源。若实际开发资源不足，应联系分配员申请调整，而非自行判断平台配置失效。

## 可写层磁盘上限

可写层磁盘上限仅限制：

- 容器自身系统层写入

不限制：

- 挂载目录
- 独立数据盘
- Docker volume

因此，大文件及长期保留数据应优先存储在挂载目录。

## GPU 使用

若容器被分配 GPU，可通过以下命令检查：

```bash
nvidia-smi
```

若能显示 GPU 信息，表示基本可用。

用户需注意：

1. GPU 非完全私有资源
2. 平台实时统计用量
3. 长期低利用率占用将影响其他用户

建议：

- 按需启动训练或推理任务
- 任务结束后及时退出无用进程
- 模型、日志、输出结果写入挂载目录

平台将 GPU 使用量汇总至 GPU 用量页面及个人门户，长时间低利用率占用将被记录。同一使用者标识在多台服务器上的 GPU 使用将合并统计。

- 最近 30 天 GPU 卡时

## 联系分配员的场景

以下情况建议直接联系分配员：

- 需要增加 CPU、内存、PIDs 或磁盘配额
- 需要增加业务端口
- 需要更换基础镜像
- 需要备份当前环境
- 需要重建容器
- GPU 不可见或环境异常

## 常见误区

### 误区 1：将容器视为宿主机

**错误理解**

可随意修改系统环境，如同传统宿主机开发。

**正确理解**

当前环境为容器内部，不应将宿主机视为个人开发环境。

### 误区 2：数据仅存储于容器系统层

**错误理解**

容器永不重建，数据无需迁移至挂载目录。

**正确理解**

重要数据应优先存储在挂载目录，以应对容器重建场景。

### 误区 3：服务启动即可对外访问

**错误理解**

程序运行后，宿主机自动可访问。

**正确理解**

必须对照端口映射规则，确保容器内监听端口与映射规则一致。

### 误区 4：容器数据天然永久保存

**错误理解**

容器存在期间，所有数据无需迁移。

**正确理解**

容器可能被更新、备份或重建，长期保留的数据应存储在挂载目录。

## 日常使用建议

1. 代码、模型、数据统一存储在挂载目录
2. 启动服务前确认容器内监听端口与映射规则一致
3. 训练任务结束后检查是否存在残留 GPU 进程
4. 资源不足时直接联系分配员，避免自行修改宿主机配置
